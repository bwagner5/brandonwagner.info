# Scaling K8s Nodes Without Breaking the Bank or Your Sanity

Brandon Wagner, AWS

# Abstract

Kubernetes (K8s) has enabled applications to be mostly agnostic to the underlying VM infrastructure it is running on. Many clusters can benefit from the cost savings of utilizing spare VM capacity offerings, called Spot, without an application re-architecture. In this post, we will discuss some of the best practices for utilizing Amazon EC2 Spot capacity within a K8s cluster and some of the tools that will make your life easier managing the underlying VM infrastructure. We will particularly focus on Karpenter which is a new, groupless node autoscaler for K8s that builds in Spot best practices. 

# Overview

Amazon EC2 Spot instances are spare, virtual machine capacity that can be utilized at a steep discount, up to 90%, compared to On-demand EC2 instances. The underlying virtual machine between Spot and On-demand instances is identical. The only caveat when using Spot is that EC2 can reclaim a Spot instance within 2-minutes of sending an interruption notification. Interruption notifications are vended through the EC2 Instance Metadata Service (IMDS) or through Amazon EventBridge and can be handled programmatically by an application. Programmatic handling of a Spot interruption notification allows your application to gracefully shutdown or checkpoint data when the notification is received. Generally, stateless workloads like APIs, continuous integration, batch processing, and dev workloads are great candidates to run on Spot nodes. Kubernetes (K8s) is an ideal environment for running Spot instances with few, if any, changes needed to the pods running on Spot nodes.

# Spot Best Practices

Although Spot and On-demand EC2 Instances are the same underlying virtual machines, the provisioning process requires a few best practices in order to maximize the Spot discount and availability of instances. Since Spot is spare virtual machine capacity, it is possible for an instance type to become unavailable for provisioning or a running Spot instance to receive an interruption notification due to an increase in On-demand instance demand. There are several steps to take to mitigate this risk. 

First, not setting a Spot max-price when provisioning a Spot instance is generally a good strategy. Previously, the EC2 Spot pricing model was a function of other customers’ bids, meaning that a higher bid could increase the running time of a Spot instance. Today, the EC2 Spot pricing model changes based on long-term supply and demand signals. The Spot max-price is no longer a bid, but rather the max price you are willing to pay for a Spot instance. Further, Spot interruption notifications are only sent in response to capacity needed for On-demand customers or when the request’s max-price has been breached, rather than reclaiming capacity for other Spot customers based on the current bids. When a Spot max-price is not set, EC2 will default the max-price to the On-demand price. However, the vast majority of the time, Spot instances are deeply discounted compared to the on-demand price.

Second, diversifying the instance types your application can run on can drastically increase the run-time of your Spot instance before an interruption notification. EC2 maintains a massive amount of VM capacity which makes it very likely that spare capacity is always available. It is important to understand how capacity is segmented and requested in order to maximize spot discounts and ensure you are always able to receive capacity for your applications. Capacity within EC2 can be described in terms of capacity pools. A single capacity pool is the tuple of instance type and availability zone. It is possible for a capacity pool to be constrained, but it is extremely unlikely for all capacity pools to be constrained within a region. For this reason, it is important to qualify applications on multiple instance types so that you can request multiple capacity pool options within an EC2 Spot instance request. 

EC2 APIs like AutoScaling Groups and Fleet support passing multiple instance type options to convey your application’s flexibility. There is an open source tool, Amazon EC2 Instance Selector, that can assist in discovering which instance types are available in specific availability zones that can run your application based on VM resources and capabilities such as vCPUs, memory, NVMe storage, etc. The EC2 Instance Selector is a Command Line Interface (CLI) and a go library that can be extended and integrated into your own tools and automation. An alternative to passing a list of instance type options to EC2 APIs is to specify your application’s resource requirements like vCPUs, memory, storage, etc directly to the APIs and let EC2 select the instance types that meet your resource criteria at launch time. This is called Attribute Based Instance Selection and can be specified via the InstanceRequirements API on EC2 launch APIs. 

When passing multiple instance type options to EC2, it can be useful to tell EC2 how to evaluate the options to launch. This ​EC2 ​functionality is called Allocation Strategies. There are two main allocation strategies supported for Spot, Lowest-Price and Capacity-Optimized. The Lowest-Price strategy will launch the instance type option with the lowest Spot price. The Capacity-Optimized strategy will launch the instance type option with the most capacity. For most use-cases it is recommended to use the Capacity-Optimized allocation strategy because it will decrease the probability of a Spot interruption which means your instance will run for a longer period of time. Spot instances launched with the Capacity-Optimized allocation strategy are still heavily discounted compared to On-demand instances.

Lastly, there is an additional signal that your application running on Spot can watch for called a rebalance recommendation. A rebalance recommendation is an early warning that your Spot instance may receive an interruption notification soon. The event is often received before the Spot interruption notification, which gives your application more than the 2-minutes an interruption notification would give you to gracefully shutdown. When using the rebalance recommendation, multiple instance types, and the capacity-optimized allocation strategy, you have more control over when to shutdown your current Spot instance and receive a new one in a deeper capacity pool. Rebalance recommendations are vended via IMDS and Amazon EventBridge, similar to Spot interruption notifications.

# Kubernetes and Spot

Kubernetes’ node lifecycle abstractions make Spot an obvious choice for many workloads. A K8s node, no matter if it is On-demand or Spot, drains pods in the same way. Furthermore, the evicted pods will be rescheduled and recover automatically onto new or existing nodes in the cluster. 

The K8s Eviction API is a standard way of evicting pods from a node. Eviction resources are only accepted by the kube-apiserver if they do not violate a Pod Disruption Budget (PDB). If an Eviction resource is accepted, then the Pod being evicted is populated with a deletion timestamp. The kubelet where the pod is running will notice the deletion timestamp and will signal to the pod to start shutting down by sending a SIGTERM signal to the containers in the pod. An application running on K8s should handle the SIGTERM signal and perform any graceful shutdown steps before exiting. If the application takes longer than the configured termination grace period, then the kubelet will force the containers to shutdown by sending a SIGKILL signal which cannot be handled by the application. If an eviction is triggered due to a Spot interruption notification, the application will only have 2-minutes to shutdown gracefully before being forcefully terminated. There are cases where the normal eviction workflow does not happen, like when the hardware backing the node fails for some reason, but this would affect both Spot and On-demand instances.

Since graceful node shutdown must be handled for On-demand instances, extending this to Spot is often trivial. One notable difference between On-demand and Spot shutdown handling within K8s is that Spot interruption notifications are not watched by the kubelet and therefore do not trigger pod evictions by default. However, the aws-node-termination-handler is a K8s controller that can be installed to watch for Spot ITNs and rebalance recommendations in order to trigger pod evictions on the Spot node that is being interrupted. If applications can tolerate being moved around nodes every so often and are able to gracefully shutdown in a reasonable timeframe based on a SIGTERM signal, then they may be a good fit for running on Spot nodes to save significantly on costs.

If you are following Spot best practices by diversifying the instance types and availability zones that your applications can run on, then you will inherently have higher Spot availability. But there may be situations where applications cannot handle a lot of movement between nodes and for those cases it is best to use On-demand instances. There are also cases where an application could run some pod replicas on Spot nodes but need to guarantee some amount of availability. For these cases, you can use a TopologySpreadConstraint to spread your Deployment’s pods evenly across Spot and On-demand nodes. It is currently not possible to weight Spot or On-demand nodes in a TopologySpreadConstraint to accomplish a small base amount of On-demand nodes and a greater number of Spot nodes.

# Autoscaling Your Cluster

Kubernetes workloads are generally managed at the pod level. For example, if an application requires 1vCPU and 2GiB of memory per pod, the desired number of replicas can be set on the Deployment resource managing your pods, to handle the anticipated load. When traffic increases to the application, the Deployment’s desired replicas can be adjusted manually or the Horizontal Pod Autoscaler (HPA) can be used to automatically adjust the replicas based on the resource utilization of the pods. Alternatively, if the application being scaled cannot scale horizontally, you can use the Vertical Pod Autoscaler (VPA) to increase the resource requests of the pods based on resource utilization. To accommodate more or larger pods running in a cluster, more nodes will need to be provisioned.

## Cluster Autoscaler

Traditionally, the K8s Cluster Autoscaler (CAS) has been used to provision nodes for a cluster in response to pods that are not able to be scheduled onto existing capacity. CAS uses a simple interface between EC2 AutoScaling Groups (ASGs), where it raises the desired number of EC2 instances in response to pending pods that kube-scheduler cannot schedule in the cluster. CAS assumes that all instances provisioned by an ASG follow a similar resource template (vCPUs, memory, etc). This means that when pods request different resources like GPUs, NVMe ephemeral storage, or different CPU architectures, cluster administrators need to create more ASGs to provide the proper resource template for the workloads. Since Spot best practices recommend instance type flexibility to receive the best discount and availability, this causes a combinatorial explosion in the number of ASGs needed by CAS. In extreme cases, clusters could have 100+ ASGs to support combinations of instance types, availability zones, and capacity types like Spot and On-demand. When there are many ASGs, there can be scaling latency because of ASG’s asynchronous API. For example, if you have 2 ASGs, one with a resource template of 2 vCPUs and 4GiB of memory and another with 4 vCPUs and 8GiB of memory, and you need a node with 2 vCPUs and 4GiB of memory, Cluster Autoscaler will increase the desired capacity of the first ASG that exactly fulfills the requirements. However, if there is no capacity available for that resource type and since ASG is asynchronously attempting to provision the instance type, there could be a lengthy delay before failing which would signal Cluster Autoscaler to try the larger resource template ASG. 

## Karpenter

Karpenter is a new K8s node autoscaler that aims to solve some of the problems of CAS while exposing a simple, K8s-native interface through a Provisioner Custom Resource Definition (CRD). The Provisioner resource has two major sections, Requirements and Provider. The Requirements section is used to tell Karpenter what types of nodes the Provisioner is allowed to create and uses the familiar K8s Requirements API. Most requirements can be specified as K8s well-known labels like node.kubernetes.io/arch or topology.kubernetes.io/availability-zone. If a well-known K8s label does not currently exist, the karpenter.sh namespace is used. Karpenter calls Spot and On-demand capacity-types and supports them through the karpenter.sh/capacity-type label. 

A single Provisioner can be flexible to both Spot and On-demand. In this case, Karpenter will try to use Spot until capacity can no longer be launched for Spot and will then use On-demand. The other prominent section of the Provisioner resource is the Provider. The Provider is where cloud provider specific parameters are accepted such as Instance Profile, Subnets, Security Groups, tags, etc. There are a few other parameters supported directly under the Provisioner spec such as ttlSecondsAfterEmpty and ttlSecondUntilExpired. The ttlSecondsAfterEmpty parameter is used to configure when Karpenter will terminate a node after all non-daemonset pods have been removed. The ttlSecondUntilExpired parameter is a mechanism to routinely terminate nodes and replace them with new nodes. This can be useful to support node OS updates or to defragment the cluster. 

The trigger for a node scale-up will be familiar to Cluster Autoscaler users since Karpenter reacts to pending pods just like CAS. Unlike CAS, Karpenter is a groupless node autoscaler that doesn’t rely on AutoScaling Groups or any externally managed instance group infrastructure; rather, it uses synchronous instance provisioning APIs. This allows Karpenter’s Provisioner resource to accommodate varying resource templates. For example, a single Karpenter Provisioner spec can launch GPUs, Spot and On-demand capacity types, x86 and ARM CPU architectures, and more. Karpenter also supports instance type flexibility by default. When pending pods are batched by Karpenter for node provisioning, Karpenter will pass all the possible instance types that fit the workload to the cloud provider specific logic for the instance launch. Karpenter was created by AWS, but is designed to be completely vendor neutral and supports a simple cloud provider interface for anyone to implement. 

Karpenter supports Spot best practices by default. The Karpenter AWS Cloud Provider uses the EC2 Fleet API to make diverse instance type requests with allocation strategies for both Spot and On-demand. For On-demand instances, Karpenter specifies the Lowest-Price allocation strategy. For Spot instances, Karpenter uses a variant of the Capacity-Optimized allocation strategy called Capacity-Optimized-Prioritized. This Spot strategy allows Karpenter to pass a list of instance types and priorities for each. The priorities Karpenter passes are roughly set by the price of the instance type. This allows the EC2 Fleet API to provision an instance type that is both cheap and has a lot of capacity to maximize the running time of the instance before an interruption. Karpenter passes up to 20 instance type options to the EC2 Fleet API and can be flexible across availability zones depending on your pod’s requirements. Multiplying out a general 3 availability zone setup and 20 instance type options means that Karpenter can provide 60 separate capacity pools for EC2 to provision from without any extra work. It would be highly unlikely to receive an Insufficient Capacity Error with such a flexible request and very likely to receive a Spot instance that is not at risk of a near-term interruption. 

# Conclusion

Scaling Kubernetes nodes can be complicated and necessarily relies on cloud provider specific feature-sets like Spot, EC2 Fleet, and Allocation Strategies within AWS. Cluster AutoScaler has been the prominent autoscaler for Kubernetes since it relies on a common feature of cloud providers, an autoscaling group, and is widely implemented across clouds. Karpenter takes a different approach using more advanced APIs within AWS, such as EC2 Fleet, and built-in best practices for Spot usage. However, the Karpenter cloud provider API is generic and can be implemented by other cloud providers, plugging in their own APIs that offer advanced functionality. Finally, Karpenter shifts the VM infrastructure into Kubernetes, by using a CRD, rather than context switching between cloud provisioning services that are generally managed outside of Kubernetes.
